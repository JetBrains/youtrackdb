Run the full `core` suite, record the complete failure list as an artifact, and size the remaining steps against it. **Triage rule, decided here rather than per-failure later:** a failure is in scope when it is a `YTDBQueryMetricsStrategyTest` scenario or a direct consequence of the `capturedExecutionPlan()` / boundary-lifecycle contracts items 1–3 settle; everything else is pre-existing branch debt, recorded with a disposition and deferred. **If in-scope failures extend materially beyond the four known scenarios — for example the Cucumber runner is red for a boundary-lifecycle reason — that is an ESCALATE, not a step:** the track was planned at ~11–13 files and a broader remediation is a different track.
1. **Settle the `reset()` contract.** Decide whether `AbstractMatchPlanStep` should re-arm from `CLOSED` (matching `YTDBGraphStep`, which re-executes fine) or whether the test's expectation is wrong. This is the one genuine product defect; the decision needs a Decision Record either way.

   **The product-side option means re-create the plan, not restart the closed one (T2).** Mapping `CLOSED` to `REARMED` in the step's own state machine is one line, and it does not work: `AbstractExecutionStep.alreadyClosed` (`:102`) is a private sticky guard set on `close()`, `ExecutionStepInternal.reset()` defaults to a no-op with no override in `AbstractExecutionStep`, and `SelectExecutionPlan.reset()` only forwards to that no-op — so a closed plan's steps stay closed forever and re-arming restarts a dead plan, leaking cursors. The realizable shape is copy-on-re-arm via `InternalExecutionPlan.copy`, which pulls `YTDBMatchPlanStep` and `MultiPlanMatchStep` into scope. The step's test must assert the no-restart property against something a Mockito plan cannot fake — verify `copy(...)` is called and `start()` is never re-invoked on the original — because the existing mocked-plan harness would go green on a production leak.

   **Two hazards specific to the copy shape (R3, R4).** `clone()`'s isolated-child-context recipe cannot be reused verbatim at re-arm: a completed pass leaves exactly the per-run context state `MultiPlanMatchStep.clone()`'s `-ea` assert forbids, so the copy path needs its own context derivation. And after a product-side item 1 the two re-arm paths diverge — `DRAINED` rewinds in place, `CLOSED` installs a copy — so `getPlan()` returns a different object depending on which path ran. `YTDBQueryMetricsStep.capturedExecutionPlan()` reads `getPlan()`, so the metrics contract this track is fixing is itself sensitive to that divergence; pin which object the capture is expected to see.
2. **Settle the `byId` capture contract.** `g.V(rid)` surfacing a plan is plausibly an improvement; update the test to the intended contract, or suppress the capture for that shape. Whichever contract is chosen, pin the translator kill-switch explicitly in the three plan-capture scenarios — none of them does today, so a flip of the default silently re-points the assertion (T3).

   **This is not only a test-contract question (R2).** RID-bearing walks set `cacheEligible=false`, so every `g.V(rid)` lookup now compiles an **uncached** MATCH plan where the native path ran no query at all. The surfaced plan is the only signal of that, and the "suppress the capture for that shape" option would delete it. Weigh the two options against the performance question, not just the assertion: if by-id lookups are compiling throwaway plans, the finding belongs in an escalation like item 3's index-usage branch, not in a test edit.

   **The suppress option has no realization inside this track's fences (A2).** Suppressing the capture for the by-id shape naturally means not translating `g.V(rid)`, which violates this track's own "do not change what translates" invariant; the only alternative threads a new flag through translator files the track lists as out of scope. Treat suppress as **rejected on scope grounds** unless Phase B finds a third realization, and record that in the item's DR — otherwise the option reads as live and a decomposer may pick it.
3. **Decide the introspection question, and first answer whether the index is still used.** The two scan tests run at cardinalities far under `MatchExecutionPlanner.THRESHOLD` (100), so their aliases are **prefetched**: the `FetchFromClassExecutionStep` / `FetchFromIndexStep` lives under `MatchPrefetchStep`, and `MatchFirstStep` is built with a null sub-plan. **`MatchPrefetchStep` is the primary target and `MatchFirstStep` the secondary one** (its sub-plan arm is still reachable above the threshold, and Track 8's union / multi-node patterns do use it) — overriding `MatchFirstStep` alone leaves both tests red (T1). Re-frame the index-usage sub-question as "does the `+ PREFETCH` sub-plan contain a `FetchFromIndexStep`": that is where the answer lives, and `listener.planPrettyInCallback` already renders it because `MatchPrefetchStep.prettyPrint` inlines the sub-plan. Assert the fix at both cardinalities, or state in the step why only the prefetched shape is covered. If the index is *not* being used, this is a performance defect well beyond a test fix and needs its own escalation.

   **Phase A decision — take option (a), and the engine-surface tension is smaller than it looked.** The plan's `### Constraints` "Engine surface is preserved" bullet freezes "the execution steps" with two named exceptions, and `MatchFirstStep` / `MatchPrefetchStep` are MATCH execution steps, so read literally the constraint forbids the override. But five MATCH steps in the same package already override `getSubSteps()` to expose a nested plan — `HashJoinMatchStep`, `FilterNotMatchPatternStep`, `BackRefHashJoinStep`, `InvertedWhileHashJoinStep`, `CorrelatedOptionalHashJoinStep` — so the two targets are the outliers and the override is conformance to an in-package convention rather than a novel carve-out (T4). The only observable effect is `EXPLAIN` result documents gaining nested `subSteps` via `ExecutionStep.toResult`; `prettyPrint` output is byte-identical and no test asserts on MATCH `subSteps`. Phase B records this as a Decision Record and amends the plan's Constraints bullet with a third exception naming the two introspection overrides as behaviour-neutral.
4. **Close the detection hole.** A red `core` unit-test run must not survive 117 commits again. Options to weigh: undraft PR #1038, add a cheap always-on check, or trigger the existing `workflow_dispatch` on `maven-pipeline.yml` — the draft gate is a single `if` on `detect-changes`, so a manual dispatch runs the full pipeline without undrafting (T7). Any combination is admissible.

   **Whatever is chosen fires every deferred gate on this branch at once (R5)** — all modules, three OS legs, the disk-storage env, and the coverage gate over eight tracks of accumulated diff. Apply item 0's triage rule to whatever it surfaces: in-scope failures are this track's, everything else is recorded as pre-existing branch debt and deferred. Without that rule the step has no exit condition.
