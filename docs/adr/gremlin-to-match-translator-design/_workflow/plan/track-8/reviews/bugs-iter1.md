## Findings

### BG1 [blocker] Post-union suffix steps are claimed and then discarded, so the union translates to a wrong result

- **File**: `core/src/main/java/com/jetbrains/youtrackdb/internal/core/gremlin/translator/strategy/GremlinStepWalker.java:384-395` (`buildResult`, multi-plan branch), with `UnionStepRecogniser.java:104-107` and `GremlinStepWalker.java:285-311` (`dispatchAll`)
- **Issue**: after `UnionStepRecogniser` accepts, the walker keeps dispatching the remaining steps against the parent `WalkerContext`. `buildResult`'s multi-plan branch reads only `boundaryAlias`, `outputType`, `returnClass`, `shaping()`, and `postConcatOps()`; it throws away `patternBuilder`, `aliasFilters`, `notMatchExpressions`, `returnItems` / `returnAliases`, `returnDistinct`, `groupBy`, `orderBy`, `limit`, `skip`, and `inputParameters`. Only four recognisers were taught to branch on `hasUnionCarrier()` — `RangeGlobalStepRecogniser`, `DedupGlobalStepRecogniser`, `OrderGlobalStepRecogniser`, and `GremlinAggregateAssembler.configureCount`. The other nineteen entries in `PRODUCTION_RECOGNISERS` accept a post-union step, write their contribution into the discarded state, and the query returns rows that ignore the step. Two confirmed shapes:
  - `g.V().union(__.out("knows"), __.in("knows")).out("knows")` — `VertexStepRecogniser` → `GremlinPatternAssembler.claimFoldedHop` (`GremlinPatternAssembler.java:63-79`) appends the hop to the discarded parent pattern and re-pins the boundary. The parent's alias counter happens to mint `$g2m_anon_1`, which equals the canonical alias the first child pinned, so the boundary step projects the union's own vertices. The trailing hop vanishes with no null, no error, and no decline. When the aliases do not coincide (`union(__.out().out(), __.in())`, canonical `$g2m_anon_2`) the same path emits an all-null traverser stream instead.
  - `g.V().union(__.out("knows"), __.in("knows")).has("name", "Bob")` — `HasStepRecogniser` accepts on a non-null boundary and calls `ctx.putAliasFilter(boundary, …)` (`WalkerContext.java:437-449`, which validates nothing). The filter never reaches any child plan, so the query returns the unfiltered union.
- **Evidence**: `dispatchAll` has no union-aware gate; its only post-accept check is that the cursor advanced. `UnionStepRecogniser`'s trailing comment asserts "an unsupported suffix declines in its own recogniser", but that is true for exactly the four recognisers listed above. DR-U4 as originally written enforced the property structurally ("the recogniser now declines a non-exhausted cursor after the union"); commit `c6c66a62b9` replaced that single gate with per-recogniser opt-in and did not add a catch-all for the recognisers it did not touch. `UnionTraversalEquivalenceTest` covers `count`, `dedup`, `limit`, and the `order` decline, and no other suffix, so the gap is untested.
- **Refutation considered**: (a) Could the strategy reject these shapes earlier? No — `hasVertexGraphStart` (`GremlinToMatchStrategy.java:251`) and the `AbstractMatchPlanStep` idempotency scan (`:353`) both pass, and `applyTranslation` splices the `MultiPlanMatchStep` on `translation.isMultiPlan()`. (b) Could `putAliasFilter` / `claimFoldedHop` decline on an alias absent from the parent pattern? Read both: `putAliasFilter` merges into a plain map with no alias validation; `claimFoldedHop` declines only on a null boundary or an untranslatable edge label. (c) Could `walk`'s terminator invariant catch it? It asserts only that `boundaryAlias`, `outputType`, and `returnClass` are non-null — all three are set. (d) Do the aggregate recognisers happen to decline? `PropertyAggregateStepRecogniser` does, because `lastPropertyProjection()` is null after a union; `GroupStepRecogniser` / `GroupCountStepRecogniser` / `SelectStepRecogniser` / `PropertyMapStepRecogniser` do not.
- **Suggestion**: restore the structural gate. Add a post-union allow-list to `dispatchAll` — when `ctx.hasUnionCarrier()` is true, decline unless the dispatched recogniser is one of the post-concat-aware set (`RangeGlobalStepRecogniser`, `DedupGlobalStepRecogniser`, `CountGlobalStepRecogniser`, `OrderGlobalStepRecogniser`). A single allow-list keeps the property true by construction as Track 9 adds list-shaping terminators, where per-recogniser opt-in would have to be re-audited across all thirty-two registry entries every time.

### BG2 [blocker] The `count(*)` push-down drops each child's `limit`, `skip`, and `DISTINCT`, so `union(…).count()` over-counts

- **File**: `core/src/main/java/com/jetbrains/youtrackdb/internal/core/gremlin/translator/strategy/PostConcatSupport.java:25-49` (`rewriteToCountStar`), called from `GremlinToMatchStrategy.java:453-457`
- **Issue**: when the only post-concat op is `Count`, `buildChildPlans` rewrites every child's `MatchPlanInputs` to a bare `RETURN count(*)`. The rewrite sets `.groupBy(null).orderBy(null).unwind(null).limit(null).skip(null).returnDistinct(false)`. A union child that carried its own `LIMIT`, `SKIP`, or `RETURN DISTINCT` therefore counts rows the child plan would not have emitted. Concrete failures:
  - `g.V().union(__.out("knows").limit(2), __.in("knows")).count()` — the fork walk of `V().out("knows").limit(2)` sets `ctx.limit = SQLLimit(2)` (`RangeGlobalStepRecogniser.java:67`, taken because the fork's own context has no union carrier). The rewrite nulls it, so the first arm contributes the full out-degree instead of `min(2, |out|)`.
  - `g.V().union(__.out("knows").dedup(), __.in("knows")).count()` — the fork sets `returnDistinct = true` (`DedupGlobalStepRecogniser.java:51`). The rewrite clears it, so duplicate neighbours are counted.
  - `g.V().union(__.out("knows").skip(1), __.in("knows")).count()` — same shape via `ctx.setSkip`.
- **Evidence**: this is precisely the hazard the single-plan path already guards. `GremlinAggregateAssembler.hasPreAggregateCardinalityClause` (`:42-44`) declines a count that follows a captured `limit` / `skip` / `dedup`, and its Javadoc names all three outcomes, including "`out().dedup().count()` would emit `RETURN DISTINCT count(*)` and count duplicates". `configurePostUnionCount` (`:79-94`) routes around that guard entirely: its only decline is a second `Count` in `postConcatOps`. The union agreement gate does not close the hole either — `UnionStepRecogniser.java:95-100` compares `outputType`, `returnClass`, and `shaping` only, and `limit` / `skip` / `returnDistinct` live on `MatchPlanInputs`, outside the contract.
- **Refutation considered**: (a) Does the union recogniser reject a child carrying a cardinality clause? Traced the accept path: `walkFork` returns a single-plan `TranslationResult`, `isMultiPlan()` is false, the three contract fields match, so the child is accepted with its `limit` intact. (b) Would the stream-count path have been correct? Yes — with `isPushDownCountOnly` false, the children keep their own `LIMIT` / `DISTINCT` and `countConcatStream` counts the concatenated element rows, which matches Gremlin. The defect is confined to the push-down branch. (c) Is `orderBy` also a problem? No — dropping `ORDER BY` does not change a count.
- **Suggestion**: gate the push-down on the children being count-safe. In `buildChildPlans`, take the push-down only when every `childInputs.get(i)` has `limit() == null && skip() == null && !returnDistinct()`; otherwise fall through to the existing `countConcatStream` path, which already produces the right answer. Mirror the guard's rationale in a comment pointing at `hasPreAggregateCardinalityClause` so the two stay in sync.

### BG3 [should-fix] The exact-`@class` count fold matches on rendered text, so a non-literal right operand folds to a full class count

- **File**: `core/src/main/java/com/jetbrains/youtrackdb/internal/core/sql/executor/HardwiredCountOptimizations.java:80-93` (`isExactClassEqualsOnly`), reached from `MatchExecutionPlanner.java:798-805`
- **Issue**: the match is `expectedClass.equals(stripQuotes(bin.getRight().toString().trim()))`. `stripQuotes` removes a matching leading/trailing quote pair and otherwise returns the text unchanged, so an unquoted identifier on the right renders to the bare name and matches. `MATCH {class: Person, as: a, where: (@class = Person)} RETURN count(*)` therefore folds to `countClass("Person", false)` and returns the class size. Executed normally, `@class = Person` compares the record's class string against the value of a property named `Person` — null on every record — and matches nothing, so the correct answer is `0`. The fold turns a zero into the full class count.
- **Evidence**: `bin.getRight()` is an `SQLExpression`; for an identifier operand its `toString()` is the bare identifier. The left-hand guard is the same shape (`"@class".equals(bin.getLeft().toString().trim())`) but is safe because `@class` has no identifier reading. The method is newly public and newly load-bearing: `tryHardwiredMatchCount` previously refused every filtered count (the deleted `aliasFilters.get(alias) != null` early return at the old `:761`), so no filter shape could reach a fast path before this track.
- **Refutation considered**: (a) Could a parameter or variable right-hand side collide? `?` and `:param` render as `?` / `:param`, and `$var` as `$var`, none of which equal a class name. The only colliding form is a bare identifier. (b) Does the SQL parser reject `@class = Person`? No — it is a well-formed binary condition over an identifier. (c) Is the Gremlin-built AST affected? No — `MatchWhereBuilder.classEquals` always emits a string literal, so the translator path is safe; the exposure is SQL-authored MATCH only. That narrowness is why this is should-fix rather than blocker.
- **Suggestion**: match structurally instead of on rendered text. Require the right operand's base expression to be a string-literal node (`SQLExpression` → `SQLBaseExpression` → string literal) and read its value, rather than `toString()` + `stripQuotes`. The existing `HardwiredCountExactClassFilterTest` cases keep passing, and a `@class = Person` case can be added as the regression pin.

### BG4 [suggestion] `countConcatStream` closes the concatenator twice

- **File**: `core/src/main/java/com/jetbrains/youtrackdb/internal/core/gremlin/translator/step/MultiPlanMatchStep.java:359-406` (`countConcatStream`; `close` at `:382-385`, `ensure` at `:387-405`)
- **Issue**: `ensure()` drains the upstream and closes it in a `finally`; `close()` then calls `upstream.close(ctx)` again when the base releases the arming's stream (`AbstractMatchPlanStep.releaseStream`, `:451-461`). The second call re-enters `MultipleExecutionStream.close`, which re-closes the still-referenced `currentStream` — the last child's `ChildContextStream`, hence that child plan's `ExecutionStream` — for the third time overall on that object. The `ExecutionStream` interface states no idempotency requirement, so this rests on every implementation in the chain tolerating repeated close.
- **Evidence**: `MultipleExecutionStream.hasNext` already closes each child stream as it drains (`:17-20`) and `close` closes `currentStream` again (`:38-43`), so a double close of the last child is pre-existing and evidently tolerated. `countConcatStream` adds a third. The failure mode if some future stream is not idempotent is a throw out of `releaseStream` during teardown, which the base converts into a suppressed exception or a close-time failure.
- **Refutation considered**: (a) Is the second close reachable on the normal path? Yes — the base always calls `releaseStream()` on exhaustion, and `close()` on early termination. (b) Does anything today throw on a repeated close? No implementation I read does, which is why this is a suggestion rather than a defect. (c) Does the same pattern exist in `sumChildCountStreams`? No — that one closes each child stream once in its own `finally` and its `close` is a no-op (`:294-296`).
- **Suggestion**: drop the `upstream.close(ctx)` from `ensure()`'s `finally` and let `close()` own the release, or add a `boolean closed` latch. The second option also documents the invariant for the `Dedup` and `Range` wrappers, which delegate close straight through.

### BG5 [suggestion] `scalarCount` returns `0` when the child count column is not a `Number`

- **File**: `core/src/main/java/com/jetbrains/youtrackdb/internal/core/gremlin/translator/step/MultiPlanMatchStep.java:329-341`
- **Issue**: the loop takes the first column whose name differs from the boundary alias and returns `number.longValue()` if it is a `Number`, otherwise `0L`. Two properties fall out: a child count row that renders its cell as a non-`Number` contributes silently zero to the union total, and a row carrying more than one non-boundary column reads whichever the property iteration order happens to yield first. A count that quietly under-reports is worse than one that fails, because nothing downstream can tell the difference.
- **Evidence**: `rewriteToCountStar` pins exactly one `count(*)` return item with a null alias (`PostConcatSupport.java:33-35`), so today the row has a single `count(*)` column carrying a `Long`, and both properties are unobservable. The fragility is that `scalarCount`'s contract is inferred from `rewriteToCountStar`'s shape rather than asserted, and the two live in different packages.
- **Refutation considered**: (a) Can the boundary-alias column appear in a rewritten count row? No — the rewrite clears `returnItems` / `returnAliases` entirely. (b) Can the count cell be null? Only if the child plan emits a row without the aggregate, which the Step-2a `GuaranteeEmptyCountStep` path rules out; an empty child yields `{count(*): 0}`. (c) Is the sibling `AbstractMatchPlanStep.primaryProjectedValue` shaped the same way? Yes (`:669-676`), but it feeds a nullable payload rather than a numeric accumulator, so a null there is visible to the caller.
- **Suggestion**: make the mismatch loud — throw `IllegalStateException` naming the offending column and value type instead of returning `0L`, or add an `assert` that the row carries exactly one non-boundary column. Zero cost in production, and it converts a silent wrong count into a diagnosable failure.

#### C8 [REFUTED] The two `MatchPlanInputs` rebuilders drop a field
Claim: `UnionStepRecogniser.rewriteReturnAlias` (`:149-176`) and `PostConcatSupport.rewriteToCountStar` (`:25-49`) both reconstruct a `MatchPlanInputs` through the builder. Verdict: REFUTED.

#### C10 [REFUTED] Chained unions recurse without terminating or mistranslate
Claim: `g.V().union(a, b).union(c, d)` makes the second union's `recognisedPrefixSteps()` include the first `UnionStep`, so each `walkFork` re-walks a traversal that itself contains a union. That could recurse without bound, or produce a child result the outer recogniser silently accepts.

Traced one level: the fork `[GraphStep, UnionStep#1, c]` re-enters `GremlinStepWalker.walk`, whose fresh context installs its own `UnionForkHostImpl`. The inner union accepts and stashes, so the fork's `buildResult` takes the multi-plan branch and returns a carrier with `isMultiPlan() == true`. The outer `UnionStepRecogniser` checks exactly that at `:84` (`childResult == null || childResult.isMultiPlan()`) and declines the whole walk. Recursion depth is bounded by the number of `UnionStep`s in the traversal, and the outcome is a clean decline to native. The planning-time fan-out (each outer child re-walking the inner union's children) is a cost concern for `review-performance`, not a correctness defect.

Verdict: REFUTED.

#### C11 [REFUTED] `recognisedPrefixSteps()` is off by one, or reads a mutated step list
Claim: `UnionForkHostImpl.recognisedPrefixSteps` computes `unionIndex = cursor.position() - 1` (`:35-46`) over a `steps` list captured at construction (`:39`, `parent.getSteps()` — a live view). An off-by-one would fork the union itself into every child (infinite structure) or drop the last prefix step; a concurrent mutation of the parent's step list during the walk would index the wrong element.

Read `StepStreamCursor`: `position` is a raw index into the backing list, and `take()` runs `skipTransparent()` before returning `stepAt(position++)` (`:78-85`). After `UnionStepRecogniser`'s opening `cursor.take()`, `position - 1` is exactly the union's index, so `[0, unionIndex)` is every step strictly before it — transparent `NoOpBarrierStep`s included, which the fork's own cursor re-skips. Nothing mutates the parent step list between the walk's start and `buildResult`: `GremlinToMatchStrategy` only calls `TraversalHelper.removeAllSteps` after `applyTranslation` has the plans in hand, and `walkFork` clones each step into a fresh `DefaultGraphTraversal` (`:56-59`) rather than re-parenting the original, so a decline leaves the parent traversal untouched.

Verdict: REFUTED.

#### C12 [NOTE] Prefix-level `limit` / `skip` / `dedup` before a union — discarded on the carrier, re-derived per fork, and divergent for a pre-existing reason
Claim: `g.V().limit(5).union(__.out(), __.in())` captures `ctx.limit = 5` on the parent context before the union claim, and `buildResult`'s multi-plan branch discards it. That looked like a second instance of BG1 on the prefix side.

The drop is real but currently masked. `recognisedPrefixSteps()` returns every step before the union, `RangeGlobalStep` included, so each fork re-walks `V().limit(5).out()` and re-derives its own `SQLLimit`. The same holds for `dedup` (`returnDistinct`), `has` (`aliasFilters` plus the bound `?` slots), `not` (`notMatchExpressions`), and the RID-bearing flag that drives `childCacheEligible`. Nothing is lost outright.

What remains is a divergence whose root cause sits outside this track. The translated form applies `LIMIT 5` to each child's *output* rows, while Gremlin applies it to the `V()` stream before the fan-out. That is the same mismatch the single-plan path already has: no recogniser guards a hop after a captured `limit` / `skip` / `dedup` — `VertexHopRecogniser` and `GremlinPatternAssembler.claimFoldedHop` read neither — so `g.V().limit(5).out()` and `g.V().dedup().out()` mistranslate on `develop`-era code too, and no test covers either. I am not raising it as a Track 8 finding because the union path inherits rather than introduces it; the track-level observation is that the fix belongs with whoever owns the single-plan ordering rule, and that the union carrier should decline (or assert) rather than silently drop these parent-context fields once BG1's allow-list lands, so a future change that stops re-walking the full prefix cannot lose them.

Verdict: NOTE, no finding.
