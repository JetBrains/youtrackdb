## Findings

### CN1 [suggestion] Concurrent-clone isolation rests on a child-context invariant this step cannot enforce

**File:** `core/src/main/java/com/jetbrains/youtrackdb/internal/core/gremlin/translator/step/MultiPlanMatchStep.java` (line 173-178, and the declaration comments at 90-102)

**Issue.** `clone()` isolates each child by minting a fresh `BasicCommandContext` parented to the original child's context (`isolatedCtx.setParentWithoutOverridingChild(childPlan.getContext())`). Isolation is real for the child's own per-run maps, but the parent — the original child plan's context — is shared by the original step and every clone. `BasicCommandContext.setVariable` and `setSystemVariable` propagate a write *up* to the parent whenever the parent already holds that key (BasicCommandContext.java:294-303 and 82-91). So if any child's template context already carries a per-run binding (`$current` / `$matched` are `VAR_CURRENT` / `VAR_MATCHED` system variables; alias / `LET` bindings are normal variables), two clones executing on two threads both write the shared parent's `variables` HashMap or its `systemVariables` `Int2ObjectOpenHashMap` — neither synchronized. That is lost updates, a corrupted open-addressing table, or an infinite probe loop, under interleaving, in a graph query. The step documents the invariant it depends on (clone comment, lines 168-172) but neither asserts nor enforces it, and the seeding decision lives in Step 3's recogniser, not here.

**Evidence.** Clone builds `isolatedCtx` per child and parents it to `childPlan.getContext()` (lines 174-177). `setParentWithoutOverridingChild` sets only `this.parent` and deliberately does not touch the parent's `child` pointer (BasicCommandContext.java:423-428), so cloning itself never mutates the shared parent — good. The residual is at *execution* time: `setSystemVariable(id, v)` → `if (parent.hasSystemVariable(id)) parent.setSystemVariable(id, v)` writes through to the shared parent for a key it already holds (BasicCommandContext.java:82-91); `setVariable` does the same for normal keys (lines 294-303). Interleaving: thread T-A drives cloneA, thread T-B drives cloneB, both reach `union` child *i* and set `$current` on their own `isolatedCtx`; if child *i*'s template context holds `VAR_CURRENT`, both writes land on the one shared `systemVariables` map concurrently. With the invariant upheld (template contexts empty), the `hasSystemVariable` guard is false on both threads and each write stays local — no shared write, no race.

**Refutation considered.** I confirmed cloning is concurrency-safe on its own: `SelectExecutionPlan.copy()` only reads the source and builds an independent chain (SelectExecutionPlan.java:238-277), and the class is documented as the per-execution thread-safety copy the plan cache relies on, so concurrent `copy()` on a shared source is by-design safe (see C2). `setParentWithoutOverridingChild` avoids the parent mutation `setParent` would cause (C2). Session writes propagate *down* only and never reach the shared parent (C3). What survives is the variable up-propagation, and it is gated on two conditions this step does not control: a child template context seeded with a per-run key at build time (Step 3), or the template step itself being iterated concurrently with a clone (which first-writes `$current` onto the template, then a concurrent clone propagates up). The single-plan `YTDBMatchPlanStep` carries the identical dependency and shipped; union widens the exposure to N multi-alias children each with `$current` / `$matched` maps, which is why the track flagged the `concurrency` category (risk R2). Contingent, not a present defect — hence suggestion, not blocker.

**Suggestion.** Convert the silent-corruption path into fail-fast: in `clone()`, after resolving each `childPlan.getContext()`, assert the template context exposes no per-run variables (empty `getVariables()` and no `VAR_CURRENT` / `VAR_MATCHED` system variable) before parenting the isolated context to it. A Java `assert` costs nothing in production and turns an invariant violation introduced by a future recogniser change into an immediate test failure rather than a load-dependent heisenbug. Independently, the Step 3 review should verify the recogniser seeds no alias / `LET` / `$matched` binding onto any child plan context at build time, and a contract test should pin it. Reference-accuracy caveat: the "template is never iterated concurrently with a clone" leg rests on TinkerPop's clone-per-execution model, which I did not verify by symbol search (PSI times out in this repo); union's `cacheEligible=false` (DR-U5) removes the plan-cache sharing path, narrowing but not formally closing it.

## Evidence base

#### C1 Shared-parent variable up-propagation under concurrent clone execution — CONFIRMED as a contingent interleaving hazard; gated on the Step-3 seed-free invariant and documented at clone() lines 168-172; survives as suggestion CN1.

#### C2 Concurrent `clone()` calls racing on the shared original (copy / getContext / parent-linking) — REFUTED.
Two threads cloning the same original both iterate `original.plans` (an immutable `List.copyOf`, read-only) and, per child, call `childPlan.getContext()` (a plain getter, SelectExecutionPlan.java:70-72), `childPlan.copy(isolatedCtx)`, and `isolatedCtx.setParentWithoutOverridingChild(origCtx)`. `SelectExecutionPlan.copy()` allocates a new plan and `copyOn` reads `this.steps` / `this.location` / `this.statement` while writing only into the fresh `copy` (SelectExecutionPlan.java:238-277) — no write to the source. The class Javadoc states copies exist precisely so the plan cache can hand one template to many threads that each `copy()` before executing, so concurrent `copy()` on a shared source is a designed-for operation. `setParentWithoutOverridingChild` writes only the new context's `parent` field and, unlike `setParent`, does not call `parent.setChild(this)` (BasicCommandContext.java:413-428), so it never mutates the shared original child context. All clone writes target the fresh `cloned` instance (`cloned.plans`, `cloned.coordinatorContext`, `resetLifecycleForClone()`), never the original. No shared mutable state is written by cloning. Residual reference-accuracy caveat: "no `ExecutionStepInternal.copy()` mutates its source" was verified for `SelectExecutionPlan.copyOn` but not exhaustively across every step subtype via PSI (times out); the single-plan step depends on the same property.

#### C3 Cross-thread session-rebind write race on a shared child context — REFUTED.
The producer's `next()` sets `childContext.setDatabaseSession(ctx.getDatabaseSession())` (MultiPlanMatchStep.java:234-235), where `ctx` is the coordinator context the base rebound in `openArming()`. For a clone, `childContext` is the copied plan's `isolatedCtx`; for the original, it is the original child context. Each step instance is iterated by exactly one thread (the base lifecycle — `state`, `openStream`, `shapedPayloads` — is plain-field, single-writer by design), and clones hold disjoint copied plans with disjoint isolated contexts, so no two threads write the same child context's session. `setDatabaseSession` propagates only *downward* to `child` (BasicCommandContext.java:521-527), and the isolated contexts have no child, so a session write never reaches the shared parent. `getDatabaseSession()`'s lazy `session = parent.getDatabaseSession()` cache-write (lines 504-518) is never triggered on the isolated context because the producer sets its session non-null before `childPlan.start()`. No shared session write under interleaving.

#### C4 Unsafe publication of the non-final `plans` / `coordinatorContext` fields — REFUTED.
Both fields are non-final for the documented JMM reason: a final field cannot be cleanly assigned after `Object.clone()` without a reflective write that voids the final-field publication guarantee, so the step uses plain writes in `clone()` and relies on a happens-before edge at publication — the same model as the reviewed `YTDBMatchPlanStep.plan`. `super.clone()` shallow-copies all base per-arming fields; `resetLifecycleForClone()` (AbstractMatchPlanStep.java:552-557) then nulls `openStream` / `armingGraph` / `shapedPayloads` and sets `state = NEW`, and `clone()` overwrites `plans` and `coordinatorContext`, so the clone carries no live reference into the original's in-flight arming. `AbstractStep.clone()` calling `reset()` on the still-aliased clone touches only `state`, not the streams (base reset() deliberately does not close `openStream`, lines 500-512), so it cannot tear down the original's cursor. For the OLTP path clone and iteration share a thread (trivially ordered); the OLAP path serializes clones with their own happens-before. No new publication defect beyond the accepted single-plan precedent.

#### C5 Compound-operation atomicity / interleaving-only leak in the stream lifecycle — REFUTED.
`startPlanStream()` builds a fresh `ExecutionStreamProducer` per arming, capturing `plans` into a local and holding a private `Iterator` (MultiPlanMatchStep.java:216-250); the producer, its iterator, and the `MultipleExecutionStream` are all confined to the single iterating thread of one arming, so `hasNext`/`next`/`close` never interleave across threads. `plans` is effectively write-once per instance (constructor or clone, both before publication) and never mutated in place, so the captured snapshot cannot shift mid-iteration. The terminal-failure and drain paths (`releaseStreamAndClosePlan` → `closePlan` closing all children including un-run ones, lines 254-283) run on the iterating thread; there is no resource acquired on one thread and released on another, so no interleaving-only leak exists. The double-close of the last child stream (concatenator close in the drain loop, then base `releaseStream`) is single-threaded and idempotent — sequential, outside this dimension.
