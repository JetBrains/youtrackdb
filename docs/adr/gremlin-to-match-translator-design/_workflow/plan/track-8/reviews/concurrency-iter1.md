## Findings

### CN1 [should-fix] The clone-isolation assert guards two of four system-variable slots, and the MATCH edge path writes an unguarded one

**File:** `core/src/main/java/com/jetbrains/youtrackdb/internal/core/gremlin/translator/step/MultiPlanMatchStep.java` (line 185-192, comment block 168-184)

**Issue.** The fail-fast assert added to close the Step-1 review's CN1 does not cover the system-variable slot that union's own child shapes write. `CommandContext` declares four slots — `VAR_CURRENT = 0`, `VAR_CURRENT_MATCH = 1`, `VAR_MATCHED = 2`, `VAR_DEPTH = 3` (`CommandContext.java:41-47`). The assert checks `VAR_CURRENT` and `VAR_MATCHED` only. `VAR_CURRENT_MATCH` and `VAR_DEPTH` are written by `MatchEdgeTraverser`, `MatchMultiEdgeTraverser`, `SQLMatchPathItem`, `LazyRecursiveTraversalStream`, and `BackRefHashJoinStep` against the context threaded in at iteration time — which, for a union child, is that child's own plan context (`ChildContextStream` supplies it deliberately). A template context carrying `VAR_CURRENT_MATCH` therefore passes the assert, and the clone's `isolatedCtx` is parented to it anyway. From that point `isolatedCtx.setSystemVariable(VAR_CURRENT_MATCH, …)` takes the write-through branch (`BasicCommandContext.java:81-91`: parent holds the key, so the write lands on the parent), and two clones driven on two threads both mutate one unsynchronised `Int2ObjectOpenHashMap`. That is a lost update, a torn open-addressing table, or a non-terminating probe loop, and the guard that was supposed to make it loud stays silent.

**Evidence.** `MatchEdgeTraverser.hasNext(ctx)` calls `computeNext(ctx)` on every candidate (line 160-170), and the candidate filter writes `VAR_CURRENT_MATCH` twice per candidate — once to `next`, once back to `previousMatch` (lines 435, 439, 442). `previousMatch` is `null` on the first candidate, so the restore performs `systemVariables.put(VAR_CURRENT_MATCH, null)`; fastutil's `Int2ObjectOpenHashMap` tracks key presence independently of the value, so `hasSystemVariable` (which uses `containsKey`, `BasicCommandContext.java:94-101`) reports `true` afterwards. `VAR_MATCHED` is written only in `next(ctx)` (line 190). A union child that matches zero rows therefore seeds `VAR_CURRENT_MATCH` on its template context and never seeds `VAR_MATCHED` or `VAR_CURRENT` — `g.V().union(out("knows"), out("employs"))` on a graph with no `employs` edges is exactly that shape, and it translates today (`UnionTraversalEquivalenceTest` covers the sibling shapes). Interleaving: thread T0 drives the original union step, child *k* matches nothing, `C_k.systemVariables` gains key `1`; TinkerPop later clones the traversal twice; the assert passes on both clones because neither guarded key is present; thread T-A drives cloneA and thread T-B drives cloneB, both reach child *k*, both call `setSystemVariable(VAR_CURRENT_MATCH, …)` on their own isolated contexts, both writes are forwarded to the single shared `C_k` map.

**Refutation considered.** The obvious escape is that `VAR_MATCHED` is written on the same code path and would trip the guard first. It is not written on the zero-row path (`MatchEdgeTraverser.next` is never reached when `hasNext` returns false), which is what makes the gap reachable rather than theoretical. The second escape is that `getVariables()` might surface system variables and catch them anyway; it does not — `BasicCommandContext.getVariables()` merges only `child.getVariables()` and the local `variables` map (lines 371-382), never `systemVariables`. The third escape is that `VAR_DEPTH` might be unreachable for union children; it is reachable through `SQLMatchPathItem`'s `while:` / recursive path items, though the current recognised union shapes do not emit those, so `VAR_CURRENT_MATCH` is the live leg. I did not find a higher-level lock: the child contexts are plain `BasicCommandContext` instances with unsynchronised maps, and nothing between `clone()` and execution serialises the two clone drives. What I could not close is whether TinkerPop's OLTP path ever clones a boundary step after that step has run — the Step-1 review left the same leg open, and union does not change it — so this stays a guard-coverage defect rather than a demonstrated production race, hence should-fix rather than blocker.

**Suggestion.** Widen the assert to reject any populated system-variable slot rather than enumerating two ids: assert that the template context holds none of `VAR_CURRENT`, `VAR_CURRENT_MATCH`, `VAR_MATCHED`, `VAR_DEPTH` (a small loop over the four constants keeps it readable and survives a fifth slot being added only if someone updates the list, so prefer exposing an `hasAnySystemVariable()` probe on `BasicCommandContext` if that is cheap). Update the assert message and the comment at lines 176-184, which currently name only `$current` / `$matched` and read as if coverage were complete. `MultiPlanMatchStepTest` already has the two fail-fast cases; add a third seeding `VAR_CURRENT_MATCH`, which fails against the current assert and passes after the fix.

### CN2 [suggestion] The metrics callback reads the clone-owned `plans` field on a thread the listener contract does not pin

**File:** `core/src/main/java/com/jetbrains/youtrackdb/internal/common/profiler/monitoring/YTDBQueryMetricsStep.java` (line 91-105, callback site 186-188)

**Issue.** `capturedExecutionPlan()` runs inside `QueryDetails.getExecutionPlan()`, an anonymous callback handed to a user-supplied `QueryMetricsListener` and evaluated whenever that listener chooses. The diff makes that callback read two pieces of state that only the query thread orders: `traversal.getSteps()` (a plain `ArrayList` on `DefaultTraversal`, mutated by `applyStrategies` / `removeAllSteps` / `addStep`) and `MultiPlanMatchStep.plans`, a deliberately non-final field written by a plain store in `clone()`. A listener that queues `QueryDetails` for an off-thread reporting pass has no happens-before edge to either write, so it can read a stale `plans` reference — the pre-clone list, which is the original step's plans, not the clone's — or iterate the step list while it is being replaced. The harm is confined to diagnostics (a wrong or null plan in a monitoring record, or an `IndexOutOfBoundsException` from the step scan), not to query results.

**Evidence.** `close()` builds the `QueryDetails` instance and passes it to `queryFinished(...)` (lines 161-191). Only `getQuerySummary()` and `getTransactionTrackingId()` read immutable state; `getQuery()` and `getExecutionPlan()` both defer work, and `getQuery()` additionally caches into an unsynchronised `cachedQuery` field (lines 166-173) — the deferred-evaluation design is intentional. `MultiPlanMatchStep.plans` is documented non-final precisely so `clone()` can install the clone's own copies with a plain write (declaration comment, `MultiPlanMatchStep.java:140-144`), which is safe under the "publish with a happens-before edge" model the step assumes and unsafe under an arbitrary reader thread. The list value itself is `List.copyOf(...)` and therefore safely publishable once its reference is visible; the exposure is the reference read, not the elements.

**Refutation considered.** I searched for an in-repo listener that defers the callback and found none — `QueryMetricsListener` is referenced only by its own file, `QueryMonitoringMode`, `YTDBQueryMetricsStep`, and `YTDBTransaction`, and the two tests in this diff read the plan synchronously inside `queryFinished`. So no shipped code triggers this today. The pattern also predates the diff: `YTDBGraphStep.getLastExecutionPlan()` is read through the same callback and is a plain field too, so the diff extends an existing exposure rather than creating one. That is why this is a suggestion. What keeps it worth recording is that `plans` is the one field in this track whose entire purpose is per-clone isolation, and an off-thread reader that sees the pre-clone value observes exactly the sharing the clone exists to prevent.

**Suggestion.** Resolve the plan eagerly in `close()` (on the query thread) and capture it into a `final` local the anonymous `QueryDetails` closes over, the same way `duration` is already captured at line 160. That costs one step-list scan per monitored query on a path that already builds a `QueryDetails` object, and it removes the thread question entirely. If the laziness is load-bearing for the un-monitored case, document on `QueryMetricsListener` that `QueryDetails` accessors must be called on the notifying thread, so an off-thread listener is a listener bug rather than an engine one.

### CN3 [suggestion] N child plans compile against N independent schema reads under one `planningStart`

**File:** `core/src/main/java/com/jetbrains/youtrackdb/internal/core/gremlin/translator/strategy/GremlinToMatchStrategy.java` (line 443-482; guard at 429, timestamp at 260)

**Issue.** `buildChildPlans` calls the plan builder once per union child in a sequential loop, and each call runs `MatchExecutionPlanner.createExecutionPlan`, which reads the live schema for class resolution, index selection, and `estimatedRootEntries`. A DDL committed by another session between child *i* and child *i+1* is visible to the later builds and invisible to the earlier ones, so one `MultiPlanMatchStep` can end up holding a mixed pre-/post-DDL plan set. The single-plan path has the same window for one plan; union is the first place where one query's answer is assembled from several independently-planned schema snapshots.

**Evidence.** `planningStart` is captured once, before the walk (line 260), and threaded unchanged into every child build (line 471). The concurrent-DDL guard at line 429 reads `GremlinPlanCache.getLastInvalidation(session) < planningStart` at *put* time, so it is conservative for the cache: a DDL landing mid-loop makes `lastInvalidation` exceed `planningStart` and every later child skips its `put`, while `AbstractMetadataUpdateCache.invalidate()` calls `cache.invalidateAll()` and wipes the entries earlier children already wrote (`AbstractMetadataUpdateCache.java:77-81`). Nothing re-checks the timestamp after the loop, so the in-flight plan list this query is about to execute keeps the torn snapshot. Interleaving: thread T1 captures `planningStart = t0`, walks, builds child 0 against schema S0 and caches it; thread T2 commits `DROP INDEX` at `t1 > t0`, which invalidates the cache; T1 builds child 1 against schema S1 and skips the put; T1 splices a step whose child 0 plan still references the dropped index.

**Refutation considered.** The first escape is that the cache guard already covers this; it covers cache *pollution* (verified above) and not the plan set handed to this execution. The second is that the built plans might resolve schema objects lazily at execution time, making the snapshot irrelevant — that is true for the count fast path by design (`HardwiredCountOptimizations.tryMatchCountFromClass` counts by class *name* at execution time, and `CountFromClassStep.canBeCached()` returns `false`), but not for index-selection decisions baked into the step chain at build time. The third is that the mid-build throw path already handles this — it handles a child build that *fails* (`closePlans` at 478-481, then the `apply` safety net declines to native), which is the benign outcome; the reported case is the one where every child build succeeds against different schemas. The realistic worst case is an execution-time exception from a step pointing at a dropped index, which the single-plan path can also produce, so this is a widened accepted risk rather than a new failure mode — suggestion, not should-fix.

**Suggestion.** Re-check the guard after the loop and before the splice: if `GremlinPlanCache.getLastInvalidation(session) >= planningStart` once every child is built, close the built plans and decline, letting the traversal run natively (or re-enter `apply` for a fresh translation). That is one `AtomicLong` read per union and reuses the `closePlans` helper already present, and it collapses the N-build window to the same "all-or-nothing against one snapshot" property the single-plan path gets for free. Whichever way this is resolved, record the decision in the track's Decision Log next to DR-U5, because the current code reads as if the DDL guard covers the whole multi-plan build.

## Evidence base

#### C1 Guard-coverage gap in `MultiPlanMatchStep.clone()`'s system-variable assert — CONFIRMED; two of four `CommandContext` slots are checked and the MATCH edge path writes `VAR_CURRENT_MATCH` on the zero-row branch that leaves both checked slots clean; surfaces as should-fix CN1.

#### C2 Deferred cross-thread read of `MultiPlanMatchStep.plans` and the traversal step list through `QueryDetails.getExecutionPlan()` — CONFIRMED as a contingent hazard gated on an off-thread listener; no in-repo listener defers today and the pattern predates the diff; surfaces as suggestion CN2.

#### C3 Torn schema snapshot across the N sequential child builds in `buildChildPlans` — CONFIRMED; the DDL guard protects the plan cache but not the in-flight child plan set, and nothing re-validates after the loop; surfaces as suggestion CN3.

#### C4 Post-concat stream state (`dedup` identity set, `count` accumulator, `skip` counter) shared across threads or across armings — REFUTED.
Every post-concat stage is allocated inside `startPlanStream()` and therefore fresh per arming: `dedupConcatStream` creates `final Set<Object> seen = new HashSet<>()` on each call before capturing it in the filter lambda (`MultiPlanMatchStep.java:409-421`), `countConcatStream` and `sumChildCountStreams` each allocate a new anonymous `ExecutionStream` with its own `pending` / `computed` fields, and `SkipExecutionStream` is a fresh instance holding its own `skipped` counter. `startPlanStream()` is invoked exactly once per arming, from `openArming()`, and its result is stored in the base's `openStream` (`AbstractMatchPlanStep.java:430-443`); a re-arm goes through `rewindPlan` and a second `startPlanStream()` call, so no stage survives into a later pass with stale state. All of them are then driven by the single iterating thread of that arming through `rowProjectionSource`. The `PostConcatOp.Count.INSTANCE` / `Dedup.INSTANCE` statics are field-less records, immutable and safely published by their `static final` initialisers, and `postConcatOps` is a `List.copyOf` assigned to a `final` field. No shared mutable state, no cross-arming carry-over.

#### C5 `GremlinPlanCache` publication of per-child plans under concurrent get / put / invalidate — REFUTED.
The cache storage is a Guava `Cache` built by `CacheBuilder.newBuilder().maximumSize(size).build()`, whose `getIfPresent` / `put` / `invalidateAll` are thread-safe and provide safe publication, and the invalidation timestamp is an `AtomicLong` with `LongAdder` counters (`AbstractMetadataUpdateCache.java:20-81`). No caller ever receives the shared template: `getInternal` returns `result.copy(ctx)` for the caller's own context (`GremlinPlanCache.java:101-106`), and `putInternal` stores a copy taken against its own `copyCtx` and closed before insertion (lines 83-87), so the template is never a live plan any thread iterates. Union adds no new access shape — `buildChildPlans` reaches the cache only through the pre-existing single-plan `buildPlan` helper, once per child. The `lastGlobalTimeout` check-then-act in `getInternal` (lines 92-97) is a benign duplicate-invalidate race on an idempotent operation and is untouched by this diff.

#### C6 Two child plans sharing one `CommandContext`, or a cached child plan reused across concurrent executions — REFUTED.
Each `buildPlan` invocation allocates its own `new BasicCommandContext(session)` and every return path yields a plan bound to a fresh context: the ineligible branch returns `buildPlanUncached(...)` (which allocates its own context, `GremlinToMatchStrategy.java:484-489`), the hit branch returns `result.copy(ctx)`, and the miss branch returns `plan.copy(ctx)`. Two structurally identical union children therefore get two distinct plan instances with two distinct contexts even when both resolve to the same fingerprint. The `childPlan.getContext().setInputParameters(childParameters)` write at line 473 lands on that fresh context, once, on the planning thread before the step is published; the map it installs is already immutable (`TranslationResult`'s canonical constructor runs `childInputParameters.stream().map(Map::copyOf).toList()`), so the clone's `isolatedCtx` resolving parameters upward through `BasicCommandContext.getInputParameters()` (lines 490-496) is a read of an immutable map. `setInputParameters` writes only the local field and never propagates to a parent, unlike `setVariable` / `setSystemVariable`.

#### C7 Fork-and-re-walk in `UnionForkHostImpl` sharing mutable state with the parent traversal or the shared static walker — REFUTED.
`GremlinStepWalker.production()` is a stateless singleton over an immutable recogniser map; every walk allocates its own `WalkerContext` and `StepStreamCursor` (`GremlinStepWalker.java:246-249`), so the new `WalkerContext` fields (`unionChildInputs`, `unionChildInputParameters`, `unionChildCacheEligible`, the mutable `postConcatOps` `ArrayList`) are confined to one walk on one thread. `walkFork` builds a fresh `DefaultGraphTraversal`, adds `step.clone()` copies of the prefix and suffix, and re-enters `walk` — it never calls `applyStrategies()`, so the fork performs reads and dispatch only and cannot re-enter the strategy chain. `setStrategies(parent.getStrategies())` shares a read-only strategy registry. The whole translation runs inside `GremlinToMatchStrategy.apply` on the query thread before the traversal is iterated, so there is no second thread to interleave with. `UnionStepRecogniser.INSTANCE`, `DedupGlobalStepRecogniser`, and `RangeGlobalStepRecogniser` are field-less singletons.

#### C8 Push-down `count(*)` rewrite colliding with another walk's entry in the cross-session plan cache — REFUTED.
`buildChildPlans` applies `PostConcatSupport.rewriteToCountStar(childInputs)` before constructing the child `TranslationResult` (line 455-457), so `buildPlan` fingerprints the rewritten inputs, not the element-shaped originals. `GremlinPlanFingerprint.appendReturnProjection` renders every `returnItems` entry through `toGenericStatement` and length-prefixes each `returnAliases` entry with a presence marker (`GremlinPlanFingerprint.java:125-145`), so a `RETURN count(*)` child and a `RETURN $b AS b` child cannot share a key. The same coverage closes the canonical-alias rewrite `UnionStepRecogniser.rewriteReturnAlias` performs: a child whose RETURN alias was rewritten from `b2` to `b0` fingerprints differently from the standalone walk that would emit `b2`. Plans containing `CountFromClassStep` never enter the cache at all, because `putInternal` honours `internal.canBeCached()` and `SelectExecutionPlan.canBeCached()` ANDs over its steps while `CountFromClassStep.canBeCached()` returns `false`.

#### C9 `toString()` on parser AST shared across threads, from the two new count predicates — REFUTED.
`MatchExecutionPlanner.isBareCountStarWithoutGroupBy()` calls `returnItems.getFirst().toString()` and `HardwiredCountOptimizations.isExactClassEqualsOnly` calls `toString()` on the filter's left and right expressions. Neither touches AST that is shared across threads. On the SQL path the `MatchExecutionPlanner(SQLMatchStatement)` constructor deep-copies every mutable AST component into planner-owned fields before planning — `returnItems`, `returnAliases`, `matchExpressions`, `groupBy`, `limit`, `skip`, and the rest (`MatchExecutionPlanner.java:443-473`) — and `aliasFilters` is rebuilt into a fresh `LinkedHashMap` during `buildPatterns`. On the Gremlin path the inputs come from a `MatchPlanInputs` produced by that walk and shared with nobody. So even if a `toString()` implementation cached into a node field, the node would be thread-confined.

#### C10 Interleaving-only leak or torn advance in the lazy `MultipleExecutionStream` / `closePlan()` lifecycle across N children — REFUTED.
The producer, its private `Iterator` over the captured `childPlans` snapshot, the `MultipleExecutionStream`, and every `ChildContextStream` are allocated inside one `startPlanStream()` call and driven by the single thread that armed the step; `hasNext` / `next` / `close` never interleave across threads. `plans` is effectively write-once per instance (constructor or `clone()`, both before publication) and is an immutable `List.copyOf`, so the captured snapshot cannot shift mid-iteration. Every release path runs on that same thread: a mid-iteration throw propagates out of `MultipleExecutionStream.hasNext` into the base's terminal handler, which calls `releaseStreamAndClosePlan` and then `closePlan()`, closing all N children including the ones the producer never opened (`MultiPlanMatchStep.java:443-471`). Nothing is acquired on one thread and released on another, so there is no interleaving-only leak. The double-close of the last child stream (the drain loop closes it, then the base's `releaseStream` closes the concatenator) is sequential and idempotent, and `closePlan()`'s first-failure-primary / rest-suppressed handling is likewise single-threaded — both belong to `review-bugs` if they belong to anyone.
