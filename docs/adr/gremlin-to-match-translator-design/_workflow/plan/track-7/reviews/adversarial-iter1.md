# Adversarial review — Track 7, iteration 1 (D9 track-realization scope)

Scope per spawn: track realization only — (1) scope/sizing, (2) cross-track-episode reality, (3) invariant violation. Inline design decisions vetted at the Phase-0→1 gate (D8 union-as-concatenation, D3 all-or-nothing, the terminator taxonomy) are not re-challenged; what is challenged is whether the track file as written realizes them.

Verdict summary: the track's two core mechanisms are unrealizable as written. `MultiPlanMatchStep extends YTDBMatchPlanStep` hits a `final` class with a private single-plan lifecycle (A1); no union shape reaches or survives the recogniser under the existing start gate and standalone-child translation (A3); and the three order-less post-process flags cannot honor the design's own declared-order rule (A2). Four should-fixes pin the cache/pipeline seams, the tail sentinel and emission-path coverage, placeholder dispatch, and the JMH/Cucumber sizing. The Pre-Flight ADJUST (route flags through `ResultShaping`, inherit the post-refactor ctor) was necessary but is not sufficient: it fixed the flag-carrier staleness and left A1/A2 in place.

Tooling caveat: mcp-steroid `steroid_execute_code` timed out twice this session, so PSI audits were unavailable. Symbol facts were established by direct file reads (exact for `YTDBMatchPlanStep`, `ResultShaping`, `GremlinToMatchStrategy`, `GremlinPlanCache`, `GremlinStepWalker`), by grep over `core/src` (for `MultiPlanMatchStep` non-existence — low collision risk for a unique name, but not PSI-verified), and by `javap` on the build-resolved fork jar `gremlin-core-3.8.1-af9db90-SNAPSHOT.jar` (exact for the bytecode facts cited). Challenges that depend on these searches carry this caveat.

## Findings

### A1 [blocker]
**Certificate**: C1
**Target**: Track file `## Plan of Work` item 2 + `## Context and Orientation` ("a `YTDBMatchPlanStep` subclass"); Pre-Flight ADJUST ("`MultiPlanMatchStep` inherits the post-refactor ctor").
**Challenge**: `YTDBMatchPlanStep` is `public final` (`core/.../translator/step/YTDBMatchPlanStep.java:88`), its constructor demands exactly one `@Nonnull InternalExecutionPlan`, its lifecycle (the five-state `State` machine, `openArming`, `releaseStream`/`releaseStreamAndClosePlan`, `close`, the deep-copy `clone` with an isolated child `BasicCommandContext`) is private and hard-wired to the single `plan` field, and every projection helper (`projectOrSkip`, `projectMap`, `convertValue`, …) is private. A subclass as written inherits nothing usable: it cannot pass N plans through the ctor, cannot reach the state machine, and cannot reuse projection. The Track 3 (14-commit lifecycle rework) and Track 6 (`ResultShaping` fold, post-completion tail) episodes are exactly the history that made this class final and closed — the plan's "extends" wording predates both. The track also omits the multi-plan lifecycle entirely: item 2 covers `processNextStart` ordering and the exception path, but not `reset()` (must rewind all consumed plans and the plan index), `clone()` (must deep-copy N plans against N isolated contexts — TinkerPop clones per execution), `close()` (must close all started plans; the stated failure behavior "closes the current stream and re-throws" leaks the already-drained-but-open plans 0..N−1, since TinkerPop never auto-closes on a thrown exception — the hazard the single-plan class documents at lines 62–66), and per-plan session rebinding on each open. Finally, design.md:663–665 lists union among the terminators a list-shaper may follow (`union(...).fold()`), so the shaping/LIST machinery of item 3 must be reachable from `MultiPlanMatchStep` too — impossible while the helpers are private.
**Evidence**: `YTDBMatchPlanStep.java:88,106,177–216,260–305,447–517`; design.md:1347 says "a variant of `YTDBMatchPlanStep`", which permits a sibling; grep over `core/src` confirms `MultiPlanMatchStep` does not exist yet (caveat: grep, not PSI).
**Proposed fix**: Pin the realization in the track file before decomposition. Two viable shapes: (a) sibling class extending `AbstractStep` plus an extracted package-private row-projector/lifecycle collaborator shared with `YTDBMatchPlanStep`, or (b) explicit de-finalization with named protected seams (projection + stream lifecycle) and overridden `reset`/`close`/`clone`. Either way, item 2 must enumerate the N-plan lifecycle: close-all-started on failure, rewind-all on re-arm, deep-copy-all on clone, per-plan context rebinding, and shaping/LIST application shared with item 3.

### A2 [blocker]
**Certificate**: C2
**Target**: Plan invariant "Translator-on and translator-off produce equal result multisets for every RECOGNIZED shape" + track items 3–4 (`unfoldOutput`/`reverseOutput`/`tailLimit` as `ResultShaping` fields, "applied in declared order").
**Challenge**: Declared order is not representable in three independent fields. Design.md:672–680 requires both `reverse().unfold()` and `unfold().reverse()` to be accepted with "both flags" set and post-processors applied "in declared order", with the recogniser declining any composition whose declared order cannot be reproduced. `ResultShaping` is an unordered bundle; two booleans erase which of the two accepted orders was declared, so the boundary must hardcode one order — and whichever it picks, the other traversal diverges from native as a multiset, not merely in order. Construction: vertex with `tags = ["ab","cd"]`. Native `g.V().values("tags").reverse().unfold()` → reverse the list → emit `"cd","ab"` → multiset {ab, cd}. Native `g.V().values("tags").unfold().reverse()` → emit then reverse each string → multiset {ba, dc} (`ReverseStep` string reversal via `StringBuilder.reverse` confirmed in the af9db90 jar bytecode). A fixed-order boundary returns one multiset for both traversals → the acceptance line "All match native" fails, and the green-suite invariant breaks. The Pre-Flight ADJUST moved the flags into `ResultShaping` but preserved the order loss.
**Evidence**: `ResultShaping.java:31–45` (unordered record, `withX` layering); design.md:663–680; `javap -c ReverseStep` (StringBuilder.reverse + Collections.reverse); track-7.md:48,62.
**Proposed fix**: Replace the three fields with one ordered post-process representation on `ResultShaping` — e.g. `List<PostProcessOp>` where `TAIL` carries its `n` — applied left-to-right by the boundary. Alternative that keeps two booleans: recogniser-side normalization (`reverse().unfold()` is multiset-equivalent to `unfold()` alone, so drop the reverse flag and pin the boundary order as unfold-then-reverse) — but then the track must state the normalization rule explicitly so tests pin it. Update items 3–4 and Interfaces accordingly.

### A3 [blocker]
**Certificate**: C3
**Target**: Track item 1 (`UnionStepRecogniser`: "sub-walk each child against the registry, build one `SelectExecutionPlan` per child") + Validation line 59.
**Challenge**: No union shape both reaches the recogniser and satisfies "standalone translation target" under the code Tracks 2–6 actually shipped. (a) Start-position `g.union(t1, t2)` compiles to a `UnionStep` start step (fork `UnionStep` has `isStart()` + the `UNION_STARTER` sentinel, af9db90 jar) — `GremlinToMatchStrategy.hasVertexGraphStart` (lines 357–360) requires the start step to be a vertex-returning `GraphStep`, so the traversal is declined by the O(1) gate before any recogniser runs; `GremlinToMatchStrategy` is not in the track's modified-files list. (b) Mid-traversal `g.V().has(...).union(out(), in())` passes the gate, but its children are prefix-relative (they start with `VertexStep`, not `V()`), so "build one `SelectExecutionPlan` per child" is meaningless without replicating the accumulated prefix pattern into each child plan — and no fork/copy mechanism exists on `WalkerContext`/`MatchPatternBuilder` (Track 5's sub-walker composes predicates into WHERE, it does not fork whole patterns). (c) Either way, `BranchStep.addChildOption` appends a `ComputerAwareStep$EndStep` to every child (bytecode confirmed), an unregistered class that fails the child sub-walk under D9 exact-class dispatch unless handled — the exact hazard Track 5 solved for `WhereStartStep`/`WhereEndStep` via `TRANSPARENT_STEPS` (`GremlinStepWalker.java:108–109`).
**Evidence**: `GremlinToMatchStrategy.java:244–246,357–360`; `javap UnionStep` / `javap -c BranchStep` on `gremlin-core-3.8.1-af9db90-SNAPSHOT.jar`; `GremlinStepWalker.java:108–109`; design.md:1342–1351 (children as "standalone translation target" — coherent only for start-position union).
**Proposed fix**: Pin the in-scope union shape in the track file and name the enabling changes. If start-position union: extend the start gate (modify `GremlinToMatchStrategy`) to admit a vertex-returning `UnionStep` start whose children carry their own `GraphStep` starts, and add EndStep transparency for child sub-walks. If mid-traversal union: specify the prefix-fork mechanism (a `WalkerContext`/pattern-builder copy seam) as a named new capability — a materially larger job that should be visible in scope. If only one shape ships, the Validation section must state that the other declines.

### A4 [should-fix]
**Certificate**: C4
**Target**: Track `## Interfaces and Dependencies` (modified-files list; no mention of the translation pipeline or `GremlinPlanCache`).
**Challenge**: The pipeline Tracks 2–6 shipped is single-plan end-to-end: `TranslationResult` carries one `MatchPlanInputs`, the `MatchPlanBuilder` seam returns one `InternalExecutionPlan`, `applyTranslation` splices one boundary (`GremlinToMatchStrategy.java:377–384`), the cache key is `GremlinPlanFingerprint.fingerprint(translation.inputs())` — one inputs record — and the cache value type is a single plan (`GremlinPlanCache extends AbstractMetadataUpdateCache<String, InternalExecutionPlan>`, line 33). A union walk produces N inputs and N plans, so `GremlinToMatchTranslator`/`TranslationResult`, the strategy's build/splice path, and the walker registry all change — none is listed as modified. The cache policy for union is undecided: per-child fingerprints (each child plan cached under its own key, honoring the Track-6 `canBeCached()` gate per child — the count-disclosure fix), or a whole-union bypass mirroring the RID-bearing `markRidBearing` bypass (Track 5 R3). Track 6's episode (fingerprint omitted result-shaping → `limit(2)`/`limit(5)` collision, track-6.md:36,45) is the proven failure mode when a new walk-shaping dimension skips the fingerprint decision. Note the boundary-only flags (`tailLimit` etc.) do NOT need fingerprinting — they never enter `MatchPlanInputs`, so one cached plan legitimately serves all tail values; the track should state this so the decomposer neither over- nor under-keys.
**Evidence**: `GremlinToMatchStrategy.java:377–411`; `GremlinPlanCache.java:33,80`; `GremlinPlanFingerprint` usage at `GremlinToMatchStrategy.java:399`; track-6.md:36,45,50.
**Proposed fix**: Add `GremlinToMatchStrategy`, `GremlinToMatchTranslator`, `GremlinStepWalker`, and `ResultShaping` to the modified list; add one sentence pinning the union cache policy (recommend per-child get/put with per-child `canBeCached()`, or bypass if simpler) and one stating that boundary-only post-process flags stay out of the fingerprint by design.

### A5 [should-fix]
**Certificate**: C5
**Target**: Track items 3–4 (`tailLimit` through `ResultShaping`; post-process application).
**Challenge**: Two realization gaps, one non-gap. Non-gap first: routing an `int` through `ResultShaping` is not a category error — the record already mixes row-level booleans with a `List<String>` and the stream-level `accumulateMap` barrier flag, so a stream-level `tailLimit` fits the established pattern; the spawn-prompt's "boolean-heavy" concern dissolves on inspection. Gap 1: the unset encoding. `tail(0)` legally means "emit nothing" and `n<0` declines pre-construction, so `tailLimit == 0` cannot mean "no tail"; an implementer defaulting the field to 0 silently turns every non-tail traversal into an empty result. The sentinel (−1, or `OptionalInt`/nullable) must be pinned with the `NONE` constant's value. Gap 2: application coverage. The boundary has three emission paths — the per-row loop (`processNextStart` while-loop), the `accumulateMap` barrier (`emitAccumulatedGroupMap`, which returns directly at `YTDBMatchPlanStep.java:272–273` bypassing `projectOrSkip`), and item 3's new LIST materialization. Design.md:663–665 allows list-shapers after group/aggregate terminators (`g.V().groupCount().unfold()` → map entrySet flat-map per `UnfoldStep.flatMap`), so post-processing hooked only into the row loop silently no-ops on the barrier path. `MultiPlanMatchStep` (A1) is a fourth consumer.
**Evidence**: `ResultShaping.java:31–45`; `YTDBMatchPlanStep.java:260–327`; design.md:608–623,663–680; track-7.md:48–49,61.
**Proposed fix**: Pin the unset sentinel in the track file (and its `ResultShaping.NONE` value), and require the post-process application point to be a single shared function invoked on all emission paths (row loop, group barrier, LIST, multi-plan), with acceptance lines for `groupCount().unfold()` and empty-input `fold()` per path.
